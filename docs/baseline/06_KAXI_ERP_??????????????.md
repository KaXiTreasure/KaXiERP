## 第1编｜KAXI_ERP_技术架构选型决策书_V0.1

> 状态：已确认  
> 确认日期：2026-08-22  
> 决策范围：模块化单体、微服务、交易数据库、分析数据库及复制架构

### 1. 最终推荐

KAXI ERP V1.0 推荐采用：

```text
应用架构：模块化单体（Modular Monolith）
后端：Python + Django
交易数据库：PostgreSQL
高可用/读扩展：PostgreSQL主库 + 热备/只读副本
缓存与任务：Redis + Celery
文件存储：MinIO/S3兼容对象存储
分析数据库：ClickHouse
交易到分析同步：Transactional Outbox起步，预留CDC升级路径
部署：Docker；开发、测试、生产环境隔离
```

明确不采用：

- V1.0 不按业务模块拆成分布式微服务。
- 不为每个业务模块建立独立交易数据库。
- 不使用ClickHouse处理库存、授信、订单确认或财务交易。
- 不让业务代码同时双写PostgreSQL和ClickHouse。
- 不按仓库或SKU分库。

### 2. 为什么选择模块化单体

KAXI的核心交易经常跨越多个业务模块：

```text
订单确认
→ 价格校验
→ 授信占用
→ 库存预留
→ 指定编号锁定
→ 应收准备
```

```text
销售发货
→ 预留消耗
→ 库存出库
→ 编号状态变化
→ 物流记录
→ 应收生成
```

这些动作要求强一致。模块化单体允许不同领域模块保持代码边界，同时在需要时使用同一个PostgreSQL事务。

微服务要求各服务拥有自己的数据，通过API或消息交互。跨服务业务通常不能依赖一个数据库ACID事务，需要最终一致、Saga、补偿、消息幂等和故障恢复。这会显著增加库存、授信和财务正确性的实现与测试难度。

因此当前选择模块化单体不是简化需求，而是为ERP强一致性选择更合适的运行形态。

### 3. 模块化单体必须满足的约束

模块化单体不能写成没有边界的“大泥球”。必须执行：

#### 3.1 领域模块

```text
identity        用户、角色、权限和审批
files           文件中心
products        SPU、SKU、材质、属性和贸易资料
parties         客户、代理、供应商和地址
pricing         价格、折扣和底价
sales           销售订单和售后
purchasing      采购、收货和退货
inventory       库存余额、预留、流水和穿透
warehouse       库位、拣货、盘点和调拨
production      BOM、生产、领料和质检
packaging       包装方案、预包装和拆包
trade           内销、外贸、币种、单证和出运
finance         授信、应收应付、收付款和结算
integrations    平台、物流、货代和外部系统
reporting       运营报表和分析查询
audit           审计和状态历史
```

#### 3.2 模块交互规则

- 模块只能通过公开应用服务调用其他模块。
- 禁止页面或任务跨模块直接修改他人数据表。
- 一个模块负责其核心实体和业务规则。
- 跨模块事务由应用服务编排。
- 对外和异步事件使用版本化事件契约。
- 每个模块拥有独立测试目录、权限命名空间和迁移边界。
- 数据库表按模块前缀或独立schema组织，具体方式在ORM设计时确认。

#### 3.3 架构守护

- 自动化依赖检查，阻止未允许的模块引用。
- 关键领域服务禁止导入页面层代码。
- 库存和财务只允许通过正式服务写入。
- 架构测试纳入持续集成。

### 4. 模块化单体与微服务对比

| 维度 | 模块化单体 | 微服务 | KAXI判断 |
|---|---|---|---|
| 库存/授信强事务 | 单库事务直接保证 | 需要Saga和补偿 | 模块化单体更合适 |
| 开发和联调 | 一个代码库和发布单元 | 多服务、多契约、多环境 | 模块化单体更可控 |
| 独立部署 | 模块不能单独发布 | 服务可独立发布 | 当前并非首要需求 |
| 故障模式 | 相对集中 | 网络、消息和部分失败更多 | 模块化单体风险更低 |
| 团队要求 | 小中型团队可维护 | 需要成熟平台和服务团队 | 当前优先模块化单体 |
| 横向扩展 | 整体应用实例扩展 | 单服务独立扩展 | V1.0整体扩展足够 |
| 长期拆分 | 边界清晰后可拆 | 已是分布式 | 先建立边界再按证据拆分 |

### 5. 微服务不是永久禁止

未来只有同时满足明确条件时才拆分某个模块：

1. 单个模块需要独立扩容，整体扩容造成显著资源浪费。
2. 独立团队能够完整负责开发、测试、部署和运行。
3. 模块边界稳定，跨模块同步调用较少。
4. 可以接受最终一致，或已具备成熟的事件和补偿机制。
5. 模块发布频率与主系统明显不同。
6. 单体发布或故障域已经成为实际瓶颈，并有监控数据证明。

首批可能独立的通常是：

- 平台集成任务
- 文件处理/OCR
- 通知服务
- 报表与分析API
- 大规模导入导出

库存核心、订单确认、授信和财务交易不作为首批拆分对象。

### 6. PostgreSQL的职责

PostgreSQL是唯一交易事实源，负责：

- 商品、客户、供应商和权限主数据
- 订单、采购、生产和库存
- 价格、授信、编号和预留
- 应收、应付、收付款和结算
- 文件元数据和业务关联
- 外贸出运、装箱和单证元数据
- 审批、审计和接口幂等状态

选择理由：

- ERP是高度关系化数据。
- 库存、授信和财务依赖ACID事务、外键、唯一约束和并发锁。
- 支持JSONB处理有限的扩展属性，但核心业务保持关系模型。
- 支持声明式分区、复制和只读热备。
- Django对PostgreSQL具有成熟原生支持。

### 7. PostgreSQL主库与副本

建议生产形态：

```text
PostgreSQL主库
├── 所有交易写入
├── 强一致业务读取
├── 库存/授信/编号校验
└── 同步到热备/只读副本

PostgreSQL热备/只读副本
├── 容灾候选
├── 普通只读查询
├── 导出和审计查询
└── 可容忍轻微延迟的运营报表
```

注意：

- PostgreSQL流复制默认异步；副本可能读取到稍旧数据。
- “写入后必须立即读到”的请求继续访问主库。
- 库存可用量、授信余额、指定编号锁定和财务余额不得依赖异步副本作最终判断。
- 是否采用同步复制，需要结合网络延迟、性能和允许的数据丢失目标决定。
- 副本不是备份，仍需独立基础备份、WAL归档和恢复演练。

### 8. 分区策略

V1.0在数据库设计阶段为大表确定分区键，但不是所有表都立即分区。

候选表：

- `inventory_ledger`
- 订单状态历史
- 审计日志
- 接口事件
- 文件访问日志
- 物流轨迹
- 财务流水和成本事件

原则：

- 优先按业务发生时间范围分区。
- 分区键必须符合主要查询和归档方式。
- 分区只用于真正的大表；不把每个普通业务表复杂化。
- 建立自动创建未来分区、监控缺失分区和归档旧分区的运维任务。

### 9. ClickHouse的职责

ClickHouse只负责分析，不是交易事实源：

- 多年订单、SKU、渠道和国家趋势
- 库存周转和库龄分析
- 材质、代理和客户利润
- 生产损耗和节日季节分析
- 平台、外贸和货代经营看板
- 大规模聚合、钻取和管理层报表

禁止：

- 从ClickHouse计算最终可售库存后直接承诺订单。
- 使用ClickHouse决定授信是否可用。
- 将ClickHouse中的金额视为法定账务余额。
- 应用同时写PostgreSQL和ClickHouse并假设两次写入原子成功。

### 10. PostgreSQL到ClickHouse同步

V1.0建议分两层：

#### 10.1 交易事件

使用Transactional Outbox：

```text
业务事务
├── 写业务数据
└── 写outbox事件
        ↓
发布/同步任务
        ↓
ClickHouse
```

优点是业务数据和待发布事件处于同一PostgreSQL事务，不会因应用双写造成一边成功、一边失败。

#### 10.2 数据复制

为高数据量明细预留CDC路径：

- 从PostgreSQL WAL读取变化。
- 同步任务必须幂等、可重试、可回放。
- 保存同步位点、延迟、错误和死信。
- 可以从PostgreSQL重新构建ClickHouse分析表。
- ClickHouse故障不得阻断ERP交易。

V1.0是否直接启用CDC，取决于首年数据量和运维能力；无论采用Outbox还是CDC，数据契约从第一天定义。

### 11. Redis与Celery

Redis负责：

- 短期缓存
- 任务队列协调
- 限流和临时状态
- 可重建的会话/辅助数据

Celery负责：

- 平台订单同步
- 文件扫描和预览生成
- 单证生成
- 报表导出
- 消息提醒
- ClickHouse同步
- 重试和补偿任务

Redis不是库存、授信或财务事实源；Redis数据丢失不得造成业务账目丢失。

### 12. 文件数据库选择

文件本体使用MinIO/S3兼容对象存储；PostgreSQL保存：

- 文件元数据
- 文件版本
- 对象存储键
- 哈希
- 安全等级和权限
- 业务关联
- 分享和审计

数据库不保存大文件BLOB。对象存储与数据库必须分别备份，并运行一致性检查。

### 13. 不选择其他数据库作为交易核心

#### MySQL

MySQL 8.4 + InnoDB能够构建可靠ERP，具备事务、外键、检查约束、复制和成熟运维生态。本项目不选择MySQL不是因为它“不够快”或“不安全”，而是PostgreSQL与当前数据模型的匹配度更高：

| 对比点 | PostgreSQL | MySQL 8.4 | KAXI影响 |
|---|---|---|---|
| 核心事务 | ACID、行锁、约束 | InnoDB同样支持 | 两者均可 |
| JSON扩展查询 | JSONB可直接配合GIN、表达式索引 | JSON列通常通过生成列/表达式方式建立可用索引 | 商品和申报扩展中PostgreSQL更直接 |
| 条件索引 | 支持带谓词的Partial Index | 无对应的通用部分索引；可用其他方式模拟部分场景 | 活跃授权、有效预留、未完成任务等索引更自然 |
| 延迟约束 | 唯一、主键、外键、排他约束可按规则延迟到事务末尾 | 外键检查不提供同等通用延迟约束语义 | 复杂批量调整和顺序交换时PostgreSQL更灵活 |
| 防重叠约束 | 支持Exclusion Constraint及范围类型组合 | 通常需要应用逻辑、触发器或锁实现 | 价格有效期、临时授权、编号占用等可强化数据库保护 |
| 分区与外键 | 支持声明式分区，并可结合关系约束（仍需遵守分区唯一约束规则） | InnoDB用户定义分区表不支持外键 | 大交易表既要分区又要关系完整性时PostgreSQL更合适 |
| Django适配 | 官方后端及较丰富的PostgreSQL专用能力 | 官方支持，需严格SQL模式并注意其特性差异 | 两者都可用，PostgreSQL与现有设计更贴合 |

如果公司已有成熟MySQL运维团队、监控备份体系、规范和大量可复用基础设施，MySQL的组织优势可能超过上述技术差异。在这种情况下可以重新评估。但当前项目从零建设，且已经设计了大量关系约束、有效期规则、JSONB扩展和大表分区，因此继续选择PostgreSQL能减少变通设计和应用层补偿。

禁止同时使用MySQL和PostgreSQL共同承担ERP交易核心，这会增加事务、备份、迁移和数据一致性成本。

#### MongoDB

商品扩展属性可以使用文档模型，但订单、库存、授信和财务高度关系化；MongoDB不作为交易核心。少量灵活属性使用PostgreSQL JSONB即可。

#### Elasticsearch/OpenSearch

仅当商品和文件全文搜索达到实际需求时作为搜索索引引入，不作为主数据库。

#### ClickHouse

适合OLAP分析，不承担OLTP核心交易。

### 14. 生产部署基线

```text
负载入口
└── Nginx/HTTPS
      ↓
应用实例 × 2（无状态）
├── Django Web/API
└── Celery Worker按队列分组

数据层
├── PostgreSQL主库
├── PostgreSQL热备/只读副本
├── Redis
├── MinIO
└── ClickHouse

运维层
├── 指标监控
├── 集中日志
├── 错误告警
├── 数据库与文件备份
├──WAL归档/PITR
└── 恢复演练
```

fnOS 单文件部署使用 `compose.fnos.yaml` 的 `backend-latest`、`frontend-latest` 跟随稳定发布；正式受控部署使用 `scripts/install-fnos.sh` 自动生成密钥、校验发布包、备份并按 `repository@sha256:digest` 拉取镜像。指定版本标签用于复现和回退，Web 默认映射宿主机端口 `8088`。

如果生产仅部署在一台fnOS物理机上，即使运行多个容器也不构成真正高可用。生产高可用至少需要独立故障域，具体硬件在部署决策中确认。

### 15. 正式决策建议

建议批准：

1. **采用模块化单体，不采用V1.0分布式微服务。**
2. **PostgreSQL作为唯一交易事实源。**
3. **生产配置PostgreSQL热备/只读副本，但强一致读取进入主库。**
4. **ClickHouse作为V1.0分析数据库，不承担交易判断。**
5. **PostgreSQL通过Outbox/CDC向ClickHouse单向同步，不做业务双写。**
6. **Redis和Celery只承担缓存及异步任务，不保存最终业务事实。**
7. **MinIO/S3兼容存储保存文件本体，PostgreSQL保存元数据。**
8. **代码按未来可拆分的领域边界组织，并设置明确微服务拆分门槛。**

### 16. 后续部署阶段待确认

- PostgreSQL复制采用同步还是异步，需在RPO/RTO和硬件评估后确认。
- V1.0直接启用CDC还是先使用Transactional Outbox。
- ClickHouse、主库和副本是否部署在独立物理故障域。
- 生产环境是否仍以fnOS为主机，或使用独立服务器/云资源。

### 16.1 已确认决策

1. 采用Django模块化单体。
2. V1.0不采用分布式微服务。
3. PostgreSQL作为唯一交易事实源。
4. PostgreSQL生产架构包含热备/只读副本能力。
5. ClickHouse作为分析数据库，不参与交易判断。
6. PostgreSQL通过Outbox/CDC向ClickHouse单向同步，不进行业务双写。
7. Redis/Celery只承担缓存和异步任务。
8. MinIO/S3兼容对象存储保存文件本体，PostgreSQL保存文件元数据和关系。

### 17. 官方技术依据

- Microsoft微服务架构资料指出，微服务应拥有独立数据；跨服务无法使用一个ACID事务，通常需要最终一致和补偿机制。
- PostgreSQL官方文档说明其支持声明式分区，以及热备、流复制、同步/异步复制和只读查询。
- ClickHouse官方资料建议PostgreSQL作为交易事实源，ClickHouse承担分析，并通过CDC等方式同步。

## 第2编｜KAXI_ERP_V1.0_技术版本基线_V0.1

> 决策日期：2026-08-22  
> 状态：源码骨架基线  
> 原则：固定大版本和关键次版本，安装时锁定经过CI验证的最新安全补丁版本；不追逐预览版。

### 1. 核心版本结论

| 层 | 选型 | V1.0基线 | 决策说明 |
|---|---|---|---|
| 后端语言 | Python | 3.13.x | 已成熟维护；Django 5.2官方支持；第三方库兼容面优于刚进入生态的新系列 |
| Web框架 | Django | 5.2 LTS最新补丁 | LTS，至少获得三年安全更新 |
| API | Django REST Framework | 当前与Django 5.2兼容的稳定版，锁文件固定 | 成熟的序列化、认证、权限和OpenAPI生态 |
| PostgreSQL驱动 | psycopg | 3.x稳定版 | 使用现代psycopg，不使用已进入维护尾部的旧驱动作为新项目基线 |
| 交易数据库 | PostgreSQL | 17.x最新补丁 | 支持至2029年；比刚发布的18拥有更长生产观察期 |
| 缓存/队列 | Redis Open Source | 7.2.x最新补丁 | ERP只使用成熟缓存和队列能力；7.2受支持至2029年 |
| 异步任务 | Celery | 5.x稳定兼容版 | 与Django/Redis组合成熟；确切补丁由依赖解析与测试锁定 |
| 前端语言 | TypeScript | 5.x稳定版 | 全项目严格类型检查 |
| 前端框架 | React | 19.2.x稳定补丁 | 官方当前React 19稳定线 |
| 构建工具 | Vite | 当前稳定大版本 | 纯前后端分离SPA/PWA，不引入SSR复杂度 |
| Node.js | Node.js | 24 LTS最新补丁 | 构建工具使用LTS，不使用Current奇数/非LTS线 |
| 包管理器 | pnpm | 当前稳定大版本，通过Corepack固定 | 严格、节省空间、锁文件可复现 |
| 分析数据库 | ClickHouse | 部署时选官方稳定/LTS并锁定 | 非交易事实源，可在压测和CDC验证后独立升级 |
| 文件存储 | S3兼容对象存储 | 通过S3 API适配层锁定具体实现 | 业务代码不依赖厂商管理API；MinIO为候选实现之一 |
| 容器 | Docker/Compose | 生产支持的稳定版 | 本地一致依赖；生产是否容器编排由部署环境决定 |

### 2. 为什么选择 Python 3.13 + Django 5.2 LTS

- Django 5.2是长期支持版本，官方列出的兼容Python包括3.10至3.14。
- Python 3.13已进入多次维护补丁阶段，适合新建长期项目。
- 不直接选择Python 3.14作为首发基线，主要为了降低二进制依赖、任务队列、图像/OCR和数据库驱动的生态兼容风险。
- Python只固定`3.13`系列，补丁版本随安全修复升级；开发、CI和生产必须保持同一小版本线。

### 3. 为什么选择 PostgreSQL 17

- PostgreSQL每个大版本官方支持五年，17支持至2029年11月。
- PostgreSQL 18虽然已正式发布且支持期更长，但KAXI V1.0优先选择拥有更充分插件、驱动、备份和运维实践观察期的17。
- 每季度评估17.x安全/修复补丁并升级；不长期固定旧补丁。
- PostgreSQL大版本升级独立立项和演练，不与普通应用发布混合。

### 4. 前端路线确认

```text
React 19 + TypeScript + Vite
├── PC Web：销售、采购、财务、主数据、报表和管理后台
└── 响应式PWA：仓库扫码、盘点、拣货、装箱、生产报工和移动审批
```

- 不采用Next.js/SSR作为ERP默认运行框架：内部ERP不需要搜索引擎渲染，前后端分离更适合权限、离线壳和独立部署。
- PC与PWA共享API客户端、权限定义、领域类型和设计系统。
- 不同时维护Vue和React两套前端。
- 浏览器支持范围在真实办公设备盘点后冻结；默认支持当前和前一个主版本的Chrome/Edge。

### 5. Redis使用边界

Redis仅用于：

- Celery broker/result的受控用途。
- 短期缓存、分布式节流、短租约和非最终状态。
- WebSocket/通知等临时传递能力（如启用）。

库存、授信、订单状态、核销、凭证和任务业务结果必须落PostgreSQL。Redis数据丢失最多导致缓存重建或任务重新领取，不能造成交易事实丢失。

### 6. 对象存储选择边界

- 应用只依赖S3兼容接口：分片上传、对象版本/不可变策略、服务端加密、生命周期和预签名URL。
- PostgreSQL保存文件元数据、业务关系、版本、哈希、权限和审计；对象存储保存二进制。
- MinIO、云厂商S3兼容服务或其他自托管实现必须通过相同契约测试。
- 最终部署实现取决于生产位置、容量、备份、合规和运维能力，不能只凭本地开发便利决定。

### 7. 后端依赖类别

首批源码骨架只引入必要依赖：

| 类别 | 候选 |
|---|---|
| API | Django REST Framework、OpenAPI生成工具 |
| 数据库 | psycopg 3 |
| 配置 | 环境变量/结构化settings |
| 异步 | Celery、Redis客户端 |
| 对象存储 | S3 SDK |
| 测试 | pytest、pytest-django、覆盖率、并发/契约测试工具 |
| 质量 | Ruff、类型检查器、依赖与安全扫描 |

未形成实际需求前不引入Elasticsearch、Kafka、MongoDB、GraphQL或工作流重型引擎。

### 8. 前端依赖类别

- 路由、服务端状态查询、表单校验、表格/虚拟列表、国际化、日期金额、扫码/PWA和测试工具。
- UI组件库必须先完成ERP表格、表单、权限和无障碍原型验证后再锁定。
- 状态管理以服务器状态和局部状态为主，不默认建立庞大全局store。
- API类型从OpenAPI生成，避免前后端手工维护两套DTO。

### 9. 版本锁定方式

- Python使用`pyproject.toml`声明直接依赖，通过锁文件固定完整传递依赖和哈希。
- Node使用`package.json`的`packageManager`字段及`pnpm-lock.yaml`。
- 容器镜像使用明确版本并在生产发布记录中保存不可变digest。
- PostgreSQL、Redis和ClickHouse固定大/次版本与镜像digest，安全补丁通过专项升级合并请求更新。
- 锁文件由CI在干净环境验证；开发人员不得只修改环境而不提交锁文件。

### 10. 升级政策

| 升级类型 | 规则 |
|---|---|
| 安全补丁 | 高优先级；自动检测、测试通过后尽快发布 |
| Python/Django补丁 | 同系列持续更新，运行完整测试和迁移检查 |
| 前端补丁 | 锁文件审查、构建、单元和E2E通过后更新 |
| 数据库小版本 | 阅读发布说明、备份和预生产演练后滚动维护 |
| 大版本 | 单独ADR、兼容评估、全量回归和回退/恢复演练 |

### 11. 禁止项

- 生产使用开发版、Beta、RC 或 nightly 镜像；`latest` 仅用于 fnOS 直接 Compose 的稳定更新通道，受控部署必须使用发布清单中的镜像摘要。
- 没有锁文件或未记录digest的正式发布。
- 因某个库安装方便而降低库存、财务或权限约束。
- 同一环境混用不同PostgreSQL大版本或不同Python小版本。
- 把Redis、ClickHouse或对象存储当成交易主库。

### 12. 源码骨架进入条件

### 3. 分层职责

| 层 | 允许 | 禁止 |
|---|---|---|
| API | 认证、序列化、调用应用命令、HTTP错误映射 | 直接拼接库存/财务写逻辑 |
| Application | 用例编排、事务边界、权限命令、幂等 | 依赖具体HTTP请求对象 |
| Domain | 状态、不变量、值对象、策略和领域事件 | 调用ORM、Celery和外部网络 |
| Infrastructure | ORM、仓储、任务、外部适配器 | 向领域泄露平台特有payload |
| Query | 授权后的查询投影和报表读取 | 绕过数据/字段权限 |

### 4. 模块依赖方向

```text
shared
  ↑
system / identity / workflow / documents
  ↑
master_data / products
  ↑
pricing / inventory / finance-core
  ↑
sales / purchasing / manufacturing / prepack / trade
  ↑
integrations / analytics
```

这里的箭头表示“上层可以依赖下层公开契约”。禁止循环导入；跨模块写操作不能直接修改对方ORM模型。

### 5. 允许的跨模块交互

1. 同一强一致事务：调用对方公开的 application service/port，例如订单确认调用授信占用和库存预留服务。
2. 事务后协作：发布领域事件到Outbox，由消费者幂等处理。
3. 查询：通过公开query service或只读投影，不把对方Repository当公共API。
4. 外键：数据库可以存在跨模块外键，但所有权和写入规则仍由所属模块控制。

禁止：跨模块导入私有model后直接 `.update()`；信号中隐藏核心交易；通过共享数据库表绕开领域服务。

### 6. Shared模块边界

`shared`只允许包含：基础异常、金额/数量/币种值对象、时钟接口、ID/编号抽象、幂等工具、审计上下文、分页、Outbox基础设施和通用测试工具。

客户、SKU、订单、库存、凭证等领域概念不得放入shared。出现两个模块都想写入的“公共业务表”时必须明确唯一所有者。

### 7. Django模型规范

- 抽象基类只提供ID、审计时间、创建人、版本等真正通用字段。
- `company_id`在公司业务表强制存在；管理器不得静默注入公司而掩盖越权，查询服务显式传入授权范围。
- 状态字段使用`TextChoices`并与数据库CHECK同步。
- 金额使用`DecimalField(max_digits=20, decimal_places=6)`；汇率10位小数。
- 不使用`GenericForeignKey`表达核心业务关系。
- `JSONField`只保存扩展、快照或受控条件，不保存需要关联、汇总或约束的核心字段。
- 默认排序不写在大交易表`Meta.ordering`，查询显式排序并使用游标分页。
- 约束、索引和表名在`Meta`中显式命名，名称包含模块前缀。

### 8. 事务与事件编码规则

- 命令处理器使用明确的`transaction.atomic()`边界。
- 锁定使用Repository中命名方法，如`lock_credit_account()`，禁止散落任意`select_for_update()`。
- 事务内创建Outbox，使用`transaction.on_commit()`仅用于唤醒worker，不把它当可靠消息保存。
- 核心业务不用Django signal触发隐含扣库存、生成应收或凭证。
- Celery任务只接受标识符和版本，不传递庞大ORM对象或敏感完整payload。

### 9. API与错误模型

统一错误结构：

```json
{
  "code": "INVENTORY_INSUFFICIENT",
  "message": "可用库存不足",
  "details": {},
  "trace_id": "..."
}
```

错误码稳定且可本地化。区分验证失败、状态冲突、乐观锁冲突、权限拒绝、幂等冲突、外部依赖暂不可用和内部错误。内部堆栈不得返回客户端。

### 10. 配置与密钥

- 环境配置使用环境变量或密钥管理服务，代码库不保存生产密码和令牌。
- settings分环境但继承同一base，测试环境不得降低关键数据库约束。
- 功能开关用于安全发布，不用于长期隐藏未完成的核心流程。
- 会计、税率、价格、审批和业务政策保存在版本化业务表，不放settings。

### 11. 测试结构

- 领域单元测试不依赖数据库。
- Repository、锁、约束和事务使用真实PostgreSQL集成测试，不用SQLite替代。
- API契约测试验证OpenAPI、权限、幂等和错误码。
- 并发测试启动独立数据库连接，真实制造锁竞争。
- 事件消费者契约固定事件类型和版本，测试旧版本兼容。
- 每个模块最低要求：正常、反向、部分、重复、并发、越权和跨期用例。

### 12. 架构守护

CI检查：

- 模块依赖图和禁止导入规则。
- API层不得直接调用其他模块ORM。
- 迁移完整性和危险DDL。
- 权限码必须存在于权限注册表/机器注册源。
- Celery任务必须存在于任务注册表/机器注册源。
- 领域事件有版本和消费者契约测试。
- 财务和库存关键模型修改必须触发财务/库存专项测试集。

### 13. 可观测性

- HTTP请求、Celery任务、Outbox和外部调用共用`trace_id`。
- 日志结构化，包含模块、公司、用户、业务对象、结果和耗时，但不含敏感明文。
- 指标覆盖请求延迟、错误码、数据库查询、锁等待、任务水位、接口限流及业务差异。
- 审计日志与技术日志分离；技术日志过期不影响法定审计记录。

### 14. 源码骨架创建门槛

1. 确认Python、Django及依赖版本基线。
2. 确认前端技术路线、包管理器和OpenAPI生成策略。
3. 建立仓库、分支、代码评审和CI环境。
4. 建立本地PostgreSQL、Redis、对象存储和测试依赖。
5. 首批只创建模块边界、公共基础设施和健康检查，不提前生成缺少评审的全部业务模型。

## 第4编｜KAXI_ERP_数据库迁移顺序与发布策略_V0.1

> 目标：规定从空库到 V1.0 的建库顺序，以及上线后零/低停机数据库变更规则。  
> 工具：Django migrations 为主，必要的 PostgreSQL 约束、索引和触发器使用可审计的 SQL migration。

### 1. 迁移基本规则

- 迁移文件进入版本控制，任何环境不得手工修改正式表结构。
- 每次迁移必须有正向步骤、回退/前滚补偿方案、数据量评估和锁影响说明。
- 结构迁移与大批量数据回填分开执行。
- 生产发布采用 expand → migrate/backfill → switch → contract，不做破坏性一步变更。
- Django迁移使用确定性代码；不得依赖当前业务数据、当前时间或外部接口产生不可重演结果。
- 已执行迁移不可改写；修正使用新迁移。

### 2. 空库建库波次

| 波次 | 内容 | 依赖及完成条件 |
|---|---|---|
| DB-00 | 数据库角色、schema、扩展、时区和基础参数 | 安全评审完成；扩展限定白名单 |
| DB-01 | 公司、币种、地区、用户、组织、角色、权限、审计骨架 | 无业务表依赖 |
| DB-02 | 工作流、编号规则、字典、文件元数据、任务和Outbox | 权限及公司已建立 |
| DB-03 | 客商、地址、联系人、银行资料、商品、SKU、属性、条码、仓库库位 | 主数据导入框架可运行 |
| DB-04 | 价格、代理、授信、销售订单、订单行、变更和售后 | 商品、客户及权限完成 |
| DB-05 | 库存余额、流水、预留、批次、单件编号、仓库任务、调拨和盘点 | 商品、仓库及订单完成 |
| DB-06 | 采购、收货、验收、供应商发票匹配 | 供应商、商品、库存完成 |
| DB-07 | BOM、工艺、生产、质检、委外、包装方案和预包装 | 商品、库存、采购完成 |
| DB-08 | 贸易合同、外贸扩展、装箱、出运、单证、货代和海外仓 | 销售、库存、文件完成 |
| DB-09 | 账簿、科目、期间、会计政策、事件、规则、凭证和余额 | 公司、币种、业务主数据完成 |

每个波次通过 `migrate → constraint check → smoke test → fixture load → rollback/restore rehearsal` 后才能成为基线。

### 3. 大表上线变更模式

#### 3.1 新增非空列

```text
1. 新增可空列或带安全常量默认值的列
2. 新代码双写/兼容读取
3. 小批量回填并记录水位
4. 添加 NOT VALID 检查约束
5. VALIDATE CONSTRAINT
6. 转为 NOT NULL
7. 删除兼容代码
```

不得对大表直接执行不可控的全表重写。

#### 3.2 新增索引

- 生产大表使用 `CREATE INDEX CONCURRENTLY`，放在非原子 migration 中。
- 先检查是否已有等价/前缀索引，再创建。
- 创建后检查有效状态、大小、扫描次数和查询计划。
- 删除索引使用并发方式，至少经过一个完整业务周期观测。

#### 3.3 增加外键或检查约束

```text
ADD CONSTRAINT ... NOT VALID
→ 清理存量异常
→ VALIDATE CONSTRAINT
```

验证和锁影响必须在近似生产数据量环境演练。

#### 3.4 字段改名或拆分

先新增字段并双写，回填后切换读路径，稳定一个发布周期后再删除旧字段。API和事件payload也遵循兼容窗口。

### 4. 数据回填框架

每个回填任务保存：

- 任务编号、迁移版本、目标表和条件。
- 游标/主键水位、批大小、开始结束时间。
- 已处理、成功、跳过、失败数量。
- 重试次数、最后错误和人工处理结论。
- 运行代码版本和校验摘要。

回填按主键范围或时间窗口分批，支持暂停和从水位继续；不得用 OFFSET 扫描超大表。

### 5. 历史数据迁移流程

```text
源数据盘点
→ 字段映射与清洗规则
→ 原始文件只读归档
→ staging导入
→ 格式/引用/重复校验
→ 业务负责人修正
→ 正式批次写入
→ 数量金额余额核对
→ 负责人签字
→ 批次冻结
```

#### 5.1 建议迁移顺序

1. 公司、组织、用户和权限。
2. 字典、币种、单位、仓库和库位。
3. 客户、代理、供应商和联系人地址。
4. SPU、SKU、条码、材质、BOM和包装方案。
5. 期初单件编号、批次和库存数量。
6. 未完成销售、采购、生产、调拨和出运单据。
7. 应收、应付、预收预付、银行未达和授信占用。
8. 固定资产、薪资初始化和税务期初资料。
9. 总账科目余额及必要明细。
10. 历史文件、合同和单证关联。

#### 5.2 财务与库存切点

- 选择明确的月末/日终作为切换时点。
- 库存数量、库存金额、应收、应付、资金、资产和总账分别签字。
- 期初余额凭证与子账期初批次使用共同迁移批次号。
- 旧系统在切点后只读；增量变更必须通过正式补录批次进入ERP。
- 不把不平衡差额塞入“其他”科目或虚拟库存，差异必须形成清单并批准处理。

### 6. 发布兼容策略

| 发布阶段 | 旧代码 | 新代码 | 数据库 |
|---|---|---|---|
| Expand | 可运行 | 未启用 | 只新增兼容结构 |
| Dual | 可运行 | 双写/兼容读 | 新旧结构并存 |
| Backfill | 可运行 | 可运行 | 分批迁移历史数据 |
| Switch | 可回退 | 读新结构 | 新结构完成校验 |
| Contract | 不再支持 | 稳定运行 | 删除旧结构，延后一发布周期 |

跨版本事件和Celery任务也必须兼容发布窗口；部署前排空或版本化不兼容队列。

### 7. 回退原则

- 纯新增结构可回退应用而保留未使用列/表。
- 已写入新事实的数据优先前滚修复，不使用会丢数据的反向迁移。
- 删除、类型收窄、合并列和数据重算属于高风险迁移，必须先备份并完成恢复演练。
- 回退不能删除已经产生的订单、库存流水、凭证、收付款、文件版本或审计记录。
- 数据修复使用带批次号、审批和前后快照的修复命令。

### 8. CI/CD数据库门禁

每个合并请求自动检查：

1. Django模型与迁移一致，无漏生成迁移。
2. 迁移可从空库完整执行。
3. 从上一发布版本升级成功。
4. schema快照无未说明差异。
5. 危险操作扫描：删表、删列、改类型、非并发大表索引、不可空列。
6. SQL格式和约束命名符合规范。
7. 迁移后核心查询计划和冒烟测试通过。

### 9. 迁移验收证据

- 迁移日志和耗时。
- 迁移前后schema差异。
- 表行数、主外键、唯一约束和异常数量。
- 库存数量金额、往来余额、总账试算平衡结果。
- 文件数量、版本、哈希及对象存在性。
- 性能基线和锁等待报告。
- 回退或恢复演练报告。
- 业务、财务、技术负责人签字记录。

## 第5编｜KAXI_ERP_关键跨模块事务与并发控制规格_V0.1

> 状态：详细设计基线草案  
> 目的：明确哪些动作必须同一 PostgreSQL 事务完成，哪些只能在提交后异步执行。

### 1. 通用事务模板

```text
验证身份、权限、数据范围和幂等键
→ 读取并校验当前状态和 version_no
→ 按固定顺序锁定聚合/余额行
→ 执行业务不变量检查
→ 写业务事实、流水、状态和审计记录
→ 写同事务 Outbox
→ COMMIT
→ 异步通知、外部接口、文件处理和分析同步
```

事务内禁止调用平台、物流、银行、税务、对象存储或邮件接口。

### 2. 订单确认

#### 2.1 同一事务

1. 以 `(company_id,id)` 锁定订单头并检查草稿/待确认状态和版本。
2. 固化客户、地址、价格、折扣、税码、币种、汇率、贸易条款和履约策略快照。
3. 计算订单金额，检查最低价格和已批准例外。
4. 锁定客户授信账户，计算永久额度、临时额度、已占用、逾期及本单占用。
5. 按固定排序锁定候选库存余额，创建库存预留；不足部分按策略生成穿透需求，不虚增实物。
6. 写授信占用明细、订单确认记录、状态和审计。
7. 写 `ORDER_CONFIRMED`、`INVENTORY_RESERVED` 等 Outbox 事件。

任一步失败全部回滚。重试命中相同幂等键时返回首次结果。

#### 2.2 事务后

仓库任务生成、平台确认回传、客户通知、分析同步和生产/采购建议刷新。

### 3. 订单取消或关键变更

- 锁定订单、受影响订单行、有效预留和授信账户。
- 已履约数量不可取消；只对未履约余额创建变更/取消记录。
- 同事务释放未消耗预留和对应授信占用。
- 已产生应收、收入、发票或收款时，不回写原事实，生成售后、折让、退款或会计冲销事件。
- 外部平台回传在提交后执行；失败只影响同步状态，不反向恢复内部已批准取消。

### 4. 库存预留、释放与出库

#### 4.1 锁顺序

统一按：

```text
company_id → warehouse_id → location_id → sku_id → inventory_status_id → lot_id
```

编号型商品在余额后按 `product_serial.id` 升序锁定。任何模块不得使用相反顺序批量锁库存。

#### 4.2 预留原子条件

```sql
UPDATE erp.inv_balance
SET reserved_qty = reserved_qty + :qty,
    available_qty = available_qty - :qty,
    row_version = row_version + 1
WHERE id = :balance_id
  AND available_qty >= :qty
  AND row_version = :expected_version;
```

受影响行数必须为1，否则重新分配或返回库存冲突。

#### 4.3 销售出库同一事务

- 锁履约任务、订单行、预留、库存余额及单件编号。
- 校验拣货/复核数量不超过有效预留。
- 减少 `on_hand_qty` 和 `reserved_qty`，写不可变库存流水及成本流水。
- 消耗预留、更新订单累计发货和编号状态。
- 写成本/会计事件 Outbox；不在事务中等待凭证生成。

### 5. 调拨

- 调出确认：同事务扣减调出仓在手量、写调出流水、创建在途库存事实。
- 调入确认：锁定在途明细，减少在途并增加调入仓在手量。
- 同一主体调拨不确认收入和利润，保留原成本。
- 差异通过调拨差异单处理，不把在途直接改成已收数量。
- 任何时点实物只能属于调出、在途或调入之一。

### 6. 采购验收

#### 6.1 同一事务

1. 锁收货单、采购行和质检记录。
2. 校验 `合格+NG+待判定=实收`，累计验收不超过实收。
3. 合格数量增加指定仓库/新品区库存；NG进入异常状态/库位。
4. 更新采购行累计收货、合格、拒收数量。
5. 写库存流水、成本暂估记录及验收事实。
6. 写 `GOODS_RECEIVED`/`AP_PROVISION_REQUIRED` Outbox。

供应商发票和三单匹配不需要与验收入库同一事务；发票晚到时通过暂估和冲回处理。

### 7. 生产领料与完工

#### 7.1 领退料

- 锁生产订单、材料需求、库存余额及相关编号。
- 领料同事务减少材料库存并增加生产成本在制归集。
- 退料同事务恢复可用库存并冲减在制实际材料。
- 超领只在审批或政策允许时执行，保留标准/实际差异。

#### 7.2 完工

- 锁生产订单、在制成本、实际耗用和目标库存余额。
- 校验累计完工不超过受控计划/批准超产数量。
- 归集材料、人工、制造费用、委外和包装实际成本。
- 合格品增加成品库存；NG进入异常库存；编号型产品生成/关联唯一编号。
- 同事务写成本记录、库存流水和生产数量；Outbox触发凭证及差异分析。

人工和制造费用尚未最终归集时可形成临时成本状态，但期间关账前必须最终化并锁定。

### 8. 预包装与拆包

- 锁预包装任务、产品库存、包装物料库存和目标库位余额。
- 完工必须在同一事务转换产品库存状态、扣减包装物料并记录实际消耗。
- 预包装不创建新的虚假SKU；包装方案版本和标签快照固定。
- 拆包同事务恢复产品状态和可退包装材料；不可退部分记录损耗。
- 任一步失败不得出现产品已预包装但物料未扣，或物料已扣但产品未转换。

### 9. 收款与应收核销

#### 9.1 收款确认

- 银行/平台流水按外部唯一键幂等落库。
- 锁收款记录；确认后不可直接修改金额、币种或账户。
- 未明确客户/订单的收款进入待认领，不自动确认为收入。

#### 9.2 核销事务

1. 锁收款及所有目标应收，按应收到期日和ID排序。
2. 校验收款可用余额、应收未核销余额、客户/币种及审批例外。
3. 写核销明细，更新收款和应收余额。
4. 外币核销计算已实现汇兑差额并保存汇率证据。
5. 写 `RECEIPT_ALLOCATED` 会计事件。

反核销创建反向核销记录并恢复余额，不删除原核销。

### 10. 付款与应付核销

- 付款申请审批时固定供应商收款账户快照；账户在审批后变更必须重新复核。
- 付款执行前锁定申请、支付批次和账户快照，检查未支付余额及职责分离。
- 银行调用在事务外：事务内先创建 `processing` 支付指令；外部成功回执再以独立幂等事务确认支付。
- 超时状态不得直接认定失败并重复付款；必须查询银行状态或人工确认。
- 付款核销锁付款与目标应付，写分配及会计事件；退票创建反向资金事件。

### 11. 会计事件过账

1. 以幂等键读取/创建会计事件，锁定事件。
2. 校验公司、账簿、期间开放、政策版本和来源快照完整。
3. 选择已批准且生效的过账规则版本。
4. 生成凭证草稿和分录，校验科目可记账、辅助核算、币种和借贷平衡。
5. 正式过账时分配连续凭证号，写余额变动并标记事件已过账。
6. 凭证、分录、余额和事件状态同一事务提交。

规则或数据错误进入待复核，不修改原业务事实。已过账凭证只能冲销/更正。

### 12. 文件发布与业务关联

- 文件二进制先上传临时对象，完成哈希和恶意文件扫描后才能发布。
- 发布事务写文件版本、对象存储正式key、当前版本指针、业务关联和审计记录。
- 对象存储移动/复制不与数据库形成分布式事务：使用 `pending_publish` 状态和可重复补偿任务。
- 数据库提交失败时临时对象由清理任务回收；数据库成功但对象操作失败时文件保持不可见并重试。

### 13. 任务领取与Outbox

```sql
SELECT id
FROM erp.evt_outbox
WHERE status = 'pending' AND next_attempt_at <= CURRENT_TIMESTAMP
ORDER BY priority DESC, id
FOR UPDATE SKIP LOCKED
LIMIT :batch_size;
```

- 领取后设置租约和worker标识并快速提交，不长时间持锁。
- 发布采用至少一次语义，消费者按事件ID/业务键幂等。
- 不允许先提交业务再另起事务“尽力写Outbox”。

### 14. 死锁与重试

- 数据库死锁/序列化失败可在命令级自动重试，使用短随机退避。
- 重试前必须释放当前事务；同一幂等键保证结果唯一。
- 业务校验失败、权限失败和审批失败不自动重试。
- 达到重试上限记录冲突资源、SQL状态、trace_id和人工处理建议。

### 15. 一致性对账

| 对账 | 恒等关系 |
|---|---|
| 库存 | 期初+所有有效流水=当前余额 |
| 预留 | 预留原值=已消耗+已释放+剩余 |
| 授信 | 额度占用汇总=未转换订单占用+应收占用等策略项 |
| 应收 | 原始+调整-核销=未收余额 |
| 应付 | 原始+调整-核销=未付余额 |
| 资金 | 收付款原值-已分配=未分配余额 |
| 凭证 | 每张及每期借方=贷方 |
| 子账总账 | 应收、应付、库存、资产、薪资及税务子账=对应总账控制科目 |

对账任务只报告或阻断，不静默覆盖事实余额。

### 16. 并发验收用例

1. 100个并发请求抢同一SKU最后库存，只允许合法数量成功。
2. 两个用户同时指定同一限量编号，只允许一个成功。
3. 两个订单同时占用客户剩余授信，不得超额。
4. 同一平台订单、银行流水和Webhook重复100次只产生一个有效事实。
5. Worker在写Outbox、发消息和消费中途分别崩溃，最终不丢事件且无重复业务影响。
6. 收付款被并发核销时余额不得变负。
7. 月结与业务过账并发时，关闭期间不得出现漏入账或跨期静默写入。
8. 文件发布任一阶段失败后能够补偿，不出现可见但无对象或有对象无记录。
